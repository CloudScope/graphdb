# Lab 4 — Answers & Explanations

**1.** `["ACC-1002", "ACC-1003"]` (Bob and Carol). From Alice's account: 2 edges gets you to Bob's account (`SENT`→`RECEIVED_BY`), 4 edges gets you to Carol's. Note `*1..4` on a chain that alternates `SENT`/`RECEIVED_BY` only works cleanly *because* the schema enforces the alternation — an `Account` only ever has outgoing `SENT` edges and a `Transaction` only ever has outgoing `RECEIVED_BY` edges, so the path can't "jump the tracks" into some other combination even though we didn't spell out the alternation explicitly. That's worth sitting with: **a clean, restrictive model makes the query simpler**, not just safer — this is the payoff of the modeling work from Lesson 4, not a separate benefit.

**2.** `txn-6` (Frank → Alice, $4800), sharing `dev-0003` with the flagged `txn-5` (Eve → Frank). Neither the amount nor the sender/receiver of `txn-6` look obviously suspicious on their own — the shared device is the *only* signal, and it's invisible unless you modeled `Device` as its own node with its own relationships. If `deviceId` had been left as a string property on `Transaction` instead, this query becomes "group all transactions by a string field and look for matches" — technically possible in SQL too, but notice it stops being a graph *traversal* and becomes a table scan, which is a strictly weaker tool for a case like "what about 4 devices removed, correlated with a third signal" — exactly the kind of question a fraud-detection product like TigerGraph is built to keep fast as this pattern gets deeper (Lesson 7).

**3.** `accountChain: ["ACC-1004", "ACC-1005", "ACC-1006", "ACC-1001"]`, `edgeHops: 6` — i.e. Dave → Eve → Frank → Alice, 3 account-hops. This is the money-flow path that ends at Alice, and it passes directly through the fraudulent Eve→Frank transfer.

**4.** Ranked: `ACC-1005` (Eve) `5000`, `ACC-1006` (Frank) `4800`, `ACC-1003` (Carol) `900`, `ACC-1001` (Alice) `500`, `ACC-1004` (Dave) `300`, `ACC-1002` (Bob) `200`. Worth noticing: the fraudulent transfer and its immediate downstream hop are the two largest amounts in the entire dataset — a real fraud model would combine *this* signal (amount) with the device-sharing signal from query 2, which is exactly why production fraud-detection graphs stack many weak signals rather than relying on one.

**5.** `A → B → C → D → E`, 4 account-hops, 8 edges. This is the interesting one: combined with query 3 (`D → E → F → A`), the full transaction chain is actually a **closed loop**: `A → B → C → D → E → F → A`. Alice isn't just "one hop downstream of a fraud transaction" (from query 3) — she's also upstream of it, because the money that eventually reaches her via Frank originated, several hops earlier, from an account that *she herself* funded. A closed transaction loop is itself a classic money-laundering red flag (circular fund movement), independent of the device-sharing signal — and it's a pattern you'd never spot by looking at any single transaction in isolation, only by tracing the full path. That's the whole architectural argument for a graph model in this domain, made concrete.

## Lesson 4 check-your-understanding — answers

**1. Is `Prescription` a relationship or a node?**

Node — and for a sharper reason than "it has properties." A binary relationship connects exactly two nodes (Lesson 4). A prescription genuinely involves *three* participants with independent identity: the `Doctor` who prescribed it, the `Patient` receiving it, and the `Drug` prescribed (which you'd also want to query independently — "which patients are on Drug X" for a recall, "which drugs interact with Drug Y"). That's an n-ary relationship, same shape as `Transaction` in this lab: model the event as a node, with binary edges out to each participant (`(doctor)-[:PRESCRIBED]->(rx:Prescription)-[:FOR_PATIENT]->(patient)`, `(rx)-[:OF_DRUG]->(drug)`). `dose` and `date` live on the `Prescription` node itself — same reasoning as `roles` living on `ACTED_IN` in Lesson 3's movie example: the fact only makes sense pinned to *this specific* combination of doctor, patient, and drug, not to any one of them alone.

**2. Is the `Device` super-node a mistake or the point?**

It's the point — in this domain, finding a hyper-connected `Device` (or shared IP, shared address) *is the fraud signal itself*, and that's exactly what query 2 surfaced. It only becomes an actual performance problem in the sense flagged in Lesson 4 if you needed to do an unconstrained multi-hop traversal that happens to route *through* a device shared by thousands of unrelated transactions — every such query would have to fan out across all of them, most of which are irrelevant noise. The production fix isn't "don't model shared devices" — it's the query pattern you already used: anchor from a small, specific set of known-fraud nodes and traverse *outward* a bounded number of hops (query 2's shape), rather than running an open-ended traversal that happens to pass *through* the busy node as a waypoint. We'll formalize exactly why that distinction matters for performance in Lesson 5.
